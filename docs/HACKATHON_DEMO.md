# Защита Smart Caspian Transit за пять минут

**Тезис:** платформа показывает момент, когда небольшая задержка превращается
в потерю целого рейса, сравнивает доступные действия и сохраняет проверяемую
историю решения. В одном пульте связаны груз, погода, стыковка, документы,
стоимость и CO₂e.

## Перед показом

Откройте работающий локальный сервер. Для самостоятельного запуска из корня:

```bash
.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8765
```

Адрес главной: `http://127.0.0.1:8765/`, рабочая платформа:
`http://127.0.0.1:8765/app`. Зависимости устанавливаются из
`backend/requirements.txt`. Браузерная сборка не требуется.

Для повторяемого чистого показа используйте отдельный каталог данных через
`SCT_DATA_DIR`, сохранив основную базу. Если задан `SCT_WRITE_TOKEN`, внесите
его через «Ключ доступа». В открытом демо ключ не требуется. Сброс базы
не нужен для обычного просмотра и расчёта сценариев.

Откройте `/app/shipments/SHP-1042`, исходный маршрут через Махачкалу и Амирабад, выключите
шторм. Для демонстрации документов подготовьте файлы из [demo-kit](demo-kit/README.md).
Показываемые ниже числа относятся к исходному демо-грузу, спокойному сценарию
и демонстрационной очереди. Реальные погодные вводные или изменённый план
могут изменить результат. Для воспроизводимой проверки есть изолированный
браузерный тест `npm run test:hackathon-ui`.

## Ход демонстрации

| Время | Действие на экране | Что объяснить |
|---|---|---|
| 0:00–0:35 | Прокрутить сцену перегрузки, открыть 3D-атлас, выбрать груз | У груза есть принятый маршрут, текущее состояние и история. Карта связана с пультом. |
| 0:35–1:40 | «Стыковки» → «Пример порога» | Паром через 24 ч; погрузка закрывается через 18 ч. Задержка подвоза/терминала 13 ч + очередь 6 ч дают готовность через 19 ч: отправление через 96 ч. Сокращение очереди на 25% даёт готовность через 17,5 ч: отправление через 24 ч. |
| 1:40–2:15 | Сравнить время, стоимость, CO₂e; раскрыть стресс-сценарии | Быстрый маршрут может быть дороже и углеродоёмче. Профиль устойчивости учитывает спокойное море, шторм и дополнительную очередь. Выбор профиля не меняет принятый план. |

Кнопка «Демо» проводит сокращённую историю за 90 секунд: груз → шторм →
объезд → стыковка → ML → цифровой коридор. Демо не принимает маршруты,
не выпускает квитанции и не записывает события за пользователя.

## Что именно здесь новое

**Порог стыковки.** Обычное сложение часов скрывает дискретный эффект:
час опоздания может стоить следующего рейса. Лаборатория показывает
границу погрузки, готовность и оба исхода. Сценарий сокращения очереди
проверяется при той же задержке подвоза и одинаковых случайных реализациях.
Это контролируемое сравнение в модели; причинный эффект в реальной
логистике потребует наблюдений или эксперимента.

**Решение под неопределённостью.** Можно выбрать минимум времени,
расходов, выбросов либо вариант с наименьшим худшим отставанием по
нескольким сценариям. Парето относится к показанным кандидатам,
а не ко всем возможным маршрутам мира. Подробности — [RESILIENCE.md](RESILIENCE.md).

**Проверяемая квитанция.** Ed25519 подписывает результат проверки,
версию плана, хеши файлов и предыдущую запись. Отдельно проверяются
подпись, локальная цепочка и актуальность документов. Квитанцию можно
передать и проверить без сайта с заранее доверенным открытым ключом.
Это прототип защищённого цифрового коридора; решение таможни он не выдаёт.

**Путь к реальному ML.** Раздельные обучение, выбор, калибровка и тест;
контроль неизвестных условий; замороженный прогноз до исхода;
сверка с прибытием и экспорт истории. Изменённые планы и демо-грузы
не превращаются в реальные учебные наблюдения.

## Числа, которые можно показывать

- При указанном примере отправление меняется с **96 на 24 ч**. В симуляции
  из 1 024 прогонов доля пропусков первого окна меняется с **82,7% на 25,8%**.
  P90 прибытия при этом остаётся прежним: часть прогонов всё ещё пропускает
  рейс. Это полезно показать, чтобы не скрывать остаточный риск.
- На встроенной синтетической тестовой выборке из 120 примеров ML даёт
  MAE около **3,68 ч**, линейная базовая модель — **5,60 ч**, медианная —
  **11,48 ч**. Номинальный 90%-й интервал покрывает **110 из 120** значений.
  Текущие метрики и хеши набора публикуются в `/api/ml/info`.
- **Ни одно из этих чисел не является измеренной точностью реальных рейсов.**
  История портовых операций, подтверждённые расписания и реальные исходы
  нужны для следующего этапа пилота.

## Проверка квитанции вне сайта

После выпуска скачайте квитанцию JSON и отдельно открытый ключ издателя.
Для независимой проверки ключ должен быть получен доверенным способом,
а не выбран из самого проверяемого файла.

```bash
.venv/bin/python scripts/verify_corridor_receipt.py corridor-receipt.json \
  --public-key corridor-issuer.json
```

Код завершения 0 означает совпадение ключа, хеша и подписи. Изменение
подписанного поля даёт отказ. Офлайн-проверка не знает о новых документах
и не подтверждает актуальность оценки; это проверяет API сервиса.

## Вопросы жюри

**Где реальный блокчейн?** Требование допускает защищённый API.
Основной сценарий использует контролируемую запись, локальный журнал
и проверяемую подпись. Распределённого консенсуса здесь нет. Эксперимент
с EVM существует отдельно и не нужен для этой демонстрации.

**Кто разрешает выпуск груза?** Таможенный орган. Прототип сверяет
поля с грузом и подписывает внутреннюю оценку; подключение к таможне
не реализовано. Даже полностью заполненный чек-лист требует проверки.

**Почему расписание условное?** Подтверждённого фида отправлений пока
нет. Оператор задаёт время выхода и закрытия погрузки; период 72 ч —
допущение модели. В пилоте этот вход заменяется данными перевозчика.

**CO₂ — сертификат?** Нет. Это сравнительная оценка транспортных плеч
по указанным факторам и расстояниям; хабовые операции и холостые пробеги
не учтены. Результат помогает сравнить варианты, а не подтверждает отчётность.

**Что нужно для пилота?** Один перевозчик, согласованные события
отправления/прибытия, фактические окна паромов, очереди терминала
и формализованные правила брокера. Сначала измерить ошибки и пропуски
стыковок на отложенной истории, затем оценить эффект рекомендаций.
