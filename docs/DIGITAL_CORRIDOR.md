# Цифровой коридор и подписанная оценка документов

Во вкладке «Документы», в разделе «Цифровой коридор», диспетчер видит, какие документы нужны для оставшегося маршрута, какие поля совпали с карточкой и какие требуют внимания. Последний загруженный файл по категории имеет приоритет перед демонстрационной отметкой. Совпадение доступных полей даёт статус «Совпало». Файл без сопоставимых полей и демонстрационная отметка требуют ручной проверки.

Диспетчер может подписать текущую оценку при любом результате проверки. Квитанция сохраняет результат на этот момент, включая расхождения и отсутствующие документы. Её можно передать перевозчику или брокеру. Таможенный выпуск оформляется отдельно.

## Сценарий проверки

1. Откройте груз `SHP-1042`, вкладку «Документы» и раздел «Цифровой коридор».
2. Загрузите счёт с неверной массой или назначением. В разделе коридора проверьте строку счёта. Файлы для повторяемой демонстрации находятся в [demo-kit](demo-kit/README.md).
3. Выпустите квитанцию и сохраните JSON. Проверка исходного JSON покажет действующую подпись и актуальную оценку, даже если сама оценка содержит расхождение.
4. Загрузите исправленный счёт или примите новый план маршрута. Проверка прежней квитанции покажет `stale`, при этом подпись и запись в цепочке останутся действительными.
5. Измените подписанное поле `payload.decision` в копии JSON и проверьте её. Результат `invalid` означает, что присланный документ отличается от подписанного.

## API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/operations/{id}/corridor` | Текущая оценка, правила, ключ издателя и список квитанций груза |
| `GET /api/operations/corridor/issuer` | Открытый ключ экземпляра сервиса, после первого выпуска |
| `POST /api/operations/{id}/corridor/issue` | Выпуск под защитой существующего ключа записи, если он настроен. Тело содержит `plan_version` и `evidence_hash` из текущей оценки. Заголовок `Idempotency-Key` обязателен |
| `GET /api/operations/{id}/corridor/receipts/{receipt_id}` | Квитанция и текущий результат проверки. Параметр `download=true` возвращает подписанный JSON для передачи |
| `POST /api/operations/{id}/corridor/verify` | Проверка присланного JSON по открытому ключу сервиса и локальному журналу. Записи журнала при этом не меняются |

Если версия маршрута или хеш оценки изменились после просмотра, выпуск возвращает HTTP 409. Повтор с тем же ключом и исходными данными возвращает прежнюю квитанцию. Использование того же ключа с другой оценкой также возвращает HTTP 409.

## Что связывает квитанция

Полезная нагрузка содержит груз, версию и состав маршрута, версию правил, SHA-256 последних файлов по категориям, результаты проверок, время и порядковый номер. Оригиналы файлов остаются в хранилище. В расхождениях подписываются имена полей. Подпись Ed25519 охватывает полезную нагрузку, идентификатор издателя и хеш предыдущей квитанции того же груза.

Онлайн-проверка сообщает три отдельных результата. `signature_valid` проверяет подпись над полезной нагрузкой и предыдущим хешем. `chain_valid` проверяет хеш квитанции и её место в сохранённой цепочке. `current` проверяет, что документы, оставшиеся плечи и версия правил по-прежнему соответствуют оценке. Цепочка локальна для данного экземпляра SQLite и груза.

Закрытый ключ создаётся при первом выпуске в каталоге данных сервиса и сохраняется между перезапусками. Публичный ключ и квитанция передаются отдельно. Если сторона заранее получила доверенный файл открытого ключа, она может проверить подпись и хеш без доступа к сервису.

```bash
python scripts/verify_corridor_receipt.py corridor-receipt.json --public-key corridor-issuer.json
```

Офлайн-проверка одного файла не подтверждает его место в локальном журнале и актуальность оценки. Эти результаты доступны через API работающего сервиса. Сброс демо удаляет локальные записи квитанций. Загруженные ранее экземпляры сохраняют подпись, которую можно сверить с доверенным открытым ключом.
