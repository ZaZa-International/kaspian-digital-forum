# План улучшения продукта — Smart Caspian Transit

Дорожная карта после хакатона: от прототипа к пилоту, который можно
показать порту, таможне и республике. Упорядочено по ценности для
пользователя, а не по сложности.

**Уже есть в прототипе** (не повторять в планах): граф коридора
(11 узлов, 17 рёбер) с динамическим поиском (Dijkstra + Yen) и
перестроением при закрытии узла; ансамбль RF + HistGradientBoosting
с CSV-контрактом реальных историй; Monte Carlo P50/P90/P95; единый
сценарный движок; реестр документов и tamper-evident ledger в SQLite;
приём фактических событий; provenance; PWA с офлайн-режимом.
Всё это — демо-уровень: метки ML синтетические, загруженность портов —
демо-снимок, реестр — не DLT.

## Фаза 1 — Пилот в Махачкале (2–4 недели после хакатона)

**Цель:** один реальный груз, один реальный маршрут, измеренный результат.

- [ ] **Живые данные порта Махачкала**: загруженность причалов и очередь
      судов — сначала ручной ввод диспетчером (форма в админке), затем
      интеграция с системой порта. Сейчас это демо-снимок — главный
      пробел прототипа.
- [ ] **Адаптеры снапшотов ASCO / Курык**: ships.asco.az (статусы паромов,
      ETA) и portkuryk.kz (диспозиция судов, подходы) — первичные
      операционные источники без открытой лицензии и архива
      (docs/RESEARCH.md §6). Парсить hourly, хранить сырые снапшоты,
      дедуплицировать по (vessel, event_type, ts), delay = факт −
      последний опубликованный ETA; уважать robots/нагрузку, режим —
      внутреннее исследование до получения лицензии.
- [ ] **История рейсов**: копить факт через `POST /api/shipments/{id}/events`
      и выгружать в CSV-контракт (`SCT_ML_HISTORY_CSV`,
      docs/ML_DATA_CONTRACT.md). Через 50–100 рейсов ML обучается на
      реальных задержках с хронологическим split (пайплайн готов).
- [ ] **Погода**: live уже есть (Open-Meteo, CC BY 4.0, non-commercial
      free tier — для коммерции нужна подписка); добавить прогноз
      на 7 дней вперёд и предупреждения за 48 часов до шторма.
- [ ] **Pre-clearance с реальным пакетом документов**: загрузка сканов,
      проверка комплектности по типу груза, интеграция с API таможни
      (пилот — одна таможенная процедура, один пост). Серверные статусы
      и provenance документов уже есть — заменить симуляцию на реальный
      орган.
- [ ] **Метрика пилота**: доля грузов, пришедших в прогноз ±6 ч;
      среднее сокращение простоя на стыковке; экономия CO₂ на
      выбранных маршрутах (с верифицируемыми факторами). Без цифр
      пилот не продать.

## Фаза 2 — Коридор целиком (1–3 месяца)

- [ ] **Все узлы коридора**: Астрахань, Актау/Курык, Баку, Туркменбаши,
      Энзели, Амирабад, Астара — живые статусы, а не демо. Условные
      плечи (Махачкала–Амирабад/Энзели, KTI) — подтвердить или убрать
      по факту запуска линий.
- [ ] **Окна отправления паромов — из данных**: сейчас ожидание —
      допущение (interval/2, Uniform(0,72) в симуляции); заменить на
      статистику фактических отправлений из снапшотов ASCO/Курык.
- [ ] **Berth windows (окна швартовки)**: синхронизация ETA/ETB между
      портом, паромом и таможней — паттерн DCSA Port Call / Portchain /
      PortXchange (docs/RESEARCH.md §3–4): единая версия плана захода
      судна для всех участников, JIT-подход.
- [ ] **Уведомления**: Telegram/Max-бот для логиста — «ваш груз
      задерживается, рекомендуем альтернативу», «шторм через 36 ч»
      (лента исключений уже считает impact → action).
- [ ] **Реестр pre-clearance — в production**: текущий hash-chain —
      tamper-evident демо в SQLite, не DLT. Вынести в отдельный сервис:
      реестр таможни или DLT-сеть, электронные подписи решений,
      журнал аудита, юридически значимый документооборот (eBL-паттерн
      DCSA — без заявления юридической силы в РФ/Иране/КЗ на старте).

## Фаза 3 — Платформа (3–6 месяцев)

- [ ] **Мобильное приложение логиста**: PWA уже есть (офлайн-оболочка);
      нативный клиент — скан накладной, push о статусе груза.
- [ ] **ML на реальных данных**: обучение на накопленной истории
      (ансамбль RF+HGB уже есть), walk-forward, калибровка вероятностей
      вместо эвристики delay/(delay+18), монотонные ограничения;
      прогноз не только задержки, но и её причины; SHAP — опционально
      (сейчас окклюзионная атрибуция).
- [ ] **Биржа мощностей**: свободные места на паромах и вагонах —
      маркетплейс внутри платформы (монетизация).
- [ ] **ESG-отчётность**: отчёт по CO₂e на груз для грузоотправителей —
      сейчас это оценка по DESNZ 2026 (UK proxy) без верификации;
      для отчётности нужны локальные факторы, учёт хабов/перегрузок
      и верификация assurance-провайдером по ISO 14083 (не заявлять
      compliance до этого).
- [ ] **Мультиязычность**: русский, английский, фарси, азербайджанский,
      казахский — для всех стран коридора.

## Что нужно от партнёров (для переговоров)

| Партнёр | Что просим | Что даём |
|---|---|---|
| Порт Махачкала | Данные о загруженности, пилот на 1 маршруте | Прогноз стыковок, меньше простоев |
| Таможня (Дагестан) | Пилот pre-clearance на 1 посту | Меньше очередей, прозрачный реестр |
| РЖД / экспедиторы | История рейсов (обезличенная) | Точный прогноз, выбор маршрута |
| ASCO / порт Курык | Лицензия/соглашение на данные снапшотов | Мониторинг и прогноз задержек паромов |
| Минцифры Дагестана | Пилотный контракт, доступ к данным | Цифровой двойник хаба республики |

## Риски и как их закрываем

- **Нет живых данных портов** → начинаем с ручного ввода диспетчера
  и снапшот-адаптеров (ASCO/Курык), ценность появляется до интеграций.
- **Паромы без расписания** → честно моделируем окно отправления
  с неопределённостью (допущение подписано), уточняем по факту сбором
  событий; не выдумываем рейсы.
- **Доверие к прогнозу** → каждый прогноз объясним (причины по часам),
  метрики публикуются в самом продукте (synthetic benchmark помечен);
  реальная точность — только после накопления план/факта.
- **Масштаб** → API сейчас **stateful**: SQLite (WAL) на одном узле,
  без репликации. Для нескольких инстансов/writers — вынести состояние
  во внешний storage (PostgreSQL/очереди), сессии и кэш — отдельно;
  фронт статический, масштабируется trivially. Горизонтальное
  масштабирование — замена storage-адаптера, не переписывание логики.
