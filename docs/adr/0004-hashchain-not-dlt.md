# ADR-0004: hash-chain в SQLite как tamper-evident демо, не DLT

Дата: 2026-11-12 · Статус: принято · Цикл 4

## Контекст
Кейс: pre-clearance «на распределённом реестре ИЛИ защищённых API» (блокчейн
опционален). Полноценный DLT (ноды, консенсус, ключи) за 2 дня не довести до
честного состояния; JSON-hash-chain без авторизации позволял клиенту самому
ставить «verified» → фиктивное решение.

## Варианты
1. **Настоящий DLT (Hyperledger/eth)** — инфраструктура, ключи, время; риск
   показать «игрушечный блокчейн» с ложными заявлениями.
2. **Hash-chain + серверные правила + provenance** — механика целостности
   настоящая (изменение/удаление/перестановка записей детектируется), статусы
   назначает сервер (симуляция органа), issuer/rule_version/снимок документов
   в каждой записи; честно подписано «не DLT».
3. **Только защищённый API без реестра** — проще, но не показывает
   tamper-evidence, которую требует дух кейса.

## Решение
Вариант 2. Клиент подаёт ссылки на документы; сервер (SCT Demo Customs
Authority, симуляция, demo-rules-v1) назначает статусы: missing/submitted/
verified/rejected/expired/unknown. Ledger v2 hash = SHA-256(prev|shipment|
decision|doc_hash|rule_version|issuer). Тесты: подмена decision/issuer,
удаление, перестановка → chain_valid=false; legacy-записи верифицируются.

## Последствия
+ Демонстрируемая целостность и происхождение решений без ложных заявлений.
− Нет распределённости/юридической силы; для production — подписи, RBAC,
  внешний notarization/DLT (ROADMAP). Угрозы: компрометация процесса =
  подмена всей цепочки (демо-ограничение, задокументировано).
