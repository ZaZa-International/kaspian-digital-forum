# ADR-0001: SQLite (WAL) для runtime-состояния вместо JSON-файлов

Дата: 2026-11-12 · Статус: принято · Цикл 2

## Контекст
JSON read-modify-write терял данные: 10 параллельных созданий груза → 3 строки
(воспроизведено), повреждённый JSON молча превращался в [] и перезаписывался,
ID = len(rows)+1 collide после удалений. Compose без volume терял состояние.

## Варианты
1. **JSON + file lock + atomic replace + counter** — минимум изменений, но
   самописная конкурентность, нет транзакций между таблицами, ручной backup.
2. **SQLite (stdlib, WAL, BEGIN IMMEDIATE)** — транзакции, атомарный hash-chain
   append, монотонные ID, идемпотентность UNIQUE-ключом, ноль новых зависимостей.
3. **PostgreSQL** — промышленно, но нужен отдельный сервис/том/миграции; для
   хакатон-демо с одним процессом — избыточно и замедляет запуск.

## Решение
SQLite (вариант 2). Один короткий connection на операцию, WAL, synchronous=FULL,
схема + миграция legacy JSON один раз под lock. Docker volume sct-data.
Сброс демо: POST /api/demo/reset / scripts/reset_demo_data.py.

## Последствия
+ Конкурентные записи не теряются (тест: 12 потоков → 12 строк).
+ Персистентность переживает restart (проверено в Docker).
− Один writer-процесс; для пилота с несколькими инстансами нужен внешний
  storage (ROADMAP). Файл sct.db — runtime, в .gitignore.
